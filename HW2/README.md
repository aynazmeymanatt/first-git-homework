سؤال ۱: تفاوت نسخه‌های HTTP و دلیل استفاده از UDP در HTTP/3
HTTP/0.9
- فقط از متد GET پشتیبانی می‌کرد.
- درخواست‌ها بسیار ساده بودند و فقط مسیر منبع را مشخص می‌کردند.
- هدر، کد وضعیت و قابلیت ارسال انواع مختلف محتوا وجود نداشت؛ پاسخ معمولاً یک فایل HTML بود.
HTTP/1.0
- هدرهای درخواست و پاسخ و کدهای وضعیت اضافه شدند.
- امکان ارسال انواع مختلف محتوا، مثل تصویر و فایل، فراهم شد.
- معمولاً برای هر درخواست یک اتصال TCP جداگانه ایجاد می‌شد.
HTTP/1.1
- اتصال پایدار (Persistent Connection) معرفی شد؛ یعنی چند درخواست می‌توانستند از یک اتصال TCP استفاده کنند.
- هدر Host امکان میزبانی چند دامنه روی یک IP را فراهم کرد.
- قابلیت‌هایی مثل کنترل بهتر کش (Cache)، انتقال تکه‌ای داده و Pipelining اضافه شدند.
HTTP/2
- داده‌ها به‌جای قالب متنی، در قالب باینری منتقل می‌شوند.
- قابلیت Multiplexing اجازه می‌دهد چند درخواست و پاسخ به‌صورت هم‌زمان روی یک اتصال TCP منتقل شوند.
- هدرها فشرده می‌شوند تا حجم داده‌های ارسالی کمتر شود.
- مشکل انتظار برای ارسال درخواست بعدی تا حد زیادی برطرف می‌شود، هرچند وابستگی به TCP همچنان می‌تواند باعث تأخیر در انتقال داده‌ها شود.
HTTP/3
- به‌جای TCP از پروتکل QUIC استفاده می‌کند که روی UDP ساخته شده است.
- قابلیت Multiplexing را دارد و اختلال در انتقال داده‌های یک جریان، برخلاف TCP، لزوماً جریان‌های دیگر را متوقف نمی‌کند.
- برقراری اتصال و راه‌اندازی ارتباط رمزگذاری‌شده می‌تواند سریع‌تر باشد.
- از رمزنگاری TLS 1.3 در ساختار QUIC استفاده می‌کند.
این تفاوت‌ها با توضیحات مرجع MDN دربارهٔ روند تکامل HTTP مطابقت دارند. 



چرا در HTTP/3 از UDP استفاده شده است؟
در TCP، داده‌ها به‌ترتیب به مقصد تحویل داده می‌شوند. اگر بخشی از داده‌ها گم شود، ممکن است دریافت داده‌های بعدی هم با تأخیر مواجه شود. در HTTP/3 از پروتکل QUIC استفاده می‌شود که بر پایه UDP ساخته شده است. QUIC خودش قابلیت‌هایی مثل اطمینان از انتقال داده، رمزنگاری و مدیریت جریان‌ها را فراهم می‌کند. در نتیجه، ارتباط می‌تواند سریع‌تر برقرار شود و گم‌شدن داده‌های یک جریان لزوماً باعث توقف جریان‌های دیگر نمی‌شود. پس UDP به‌تنهایی قابل‌اعتمادتر از TCP نیست؛ بلکه QUIC این قابلیت‌ها را روی UDP فراهم می‌کند.

سؤال ۲: ارتباط‌های Stateless و Stateful
الف) تفاوت Stateless و Stateful

در ارتباط Stateless، سرور اطلاعات درخواست‌های قبلی را برای پردازش درخواست جدید نگه نمی‌دارد و هر درخواست را مستقل بررسی می‌کند. اما در ارتباط Stateful، سرور وضعیت ارتباط یا اطلاعات قبلی کاربر را نگه می‌دارد و برای درخواست‌های بعدی از آن استفاده می‌کند. برای مثال، نگه‌داشتن وضعیت ورود کاربر در یک سایت می‌تواند با استفاده از یک نشست (Session) انجام شود.

ب) HTTP در کدام دسته قرار می‌گیرد و چگونه مشکل آن حل می‌شود؟
پروتکل HTTP ذاتاً Stateless است؛ یعنی هر درخواست به‌صورت مستقل پردازش می‌شود و سرور صرفاً با توجه به خود پروتکل، وضعیت درخواست قبلی را به خاطر نمی‌سپارد. برای حل این مشکل، از روش‌هایی مثل Cookie و Session استفاده می‌شود. سرور یک شناسهٔ نشست ایجاد می‌کند و آن را معمولاً از طریق Cookie در اختیار مرورگر قرار می‌دهد. مرورگر در درخواست‌های بعدی این شناسه را ارسال می‌کند و سرور با استفاده از آن می‌تواند کاربر را شناسایی کند و اطلاعات مربوط به نشست او را بازیابی کند.


سؤال ۳: راهکارهای ارتباطی برای محدودیت مدل Client/Server

الف) توضیح چالش:

در مدل معمول HTTP، ارتباط با درخواست کلاینت شروع می‌شود و سرور در پاسخ به آن اطلاعات می‌فرستد. بنابراین، سرور نمی‌تواند به‌صورت عادی و بدون وجود یک ارتباط یا سازوکار قبلی، اطلاعات جدید را مستقیماً به کلاینت ارسال کند. این موضوع برای کاربردهایی مثل چت آنلاین، اعلان‌های لحظه‌ای و ارسال رویدادها مشکل ایجاد می‌کند؛ چون کلاینت باید بتواند بدون ارسال مداوم درخواست‌های جدید، از اطلاعات تازه باخبر شود.

ب) راهکارهای مقابله با این چالش:

۱. Polling (نظرسنجی دوره‌ای)

در این روش، کلاینت در فاصله‌های زمانی مشخص، مثلاً هر پنج ثانیه، از سرور درخواست می‌کند که آیا اطلاعات جدیدی وجود دارد یا نه. پیاده‌سازی آن ساده است و تقریباً با همهٔ سرورها سازگاری دارد؛ اما اگر اطلاعات جدیدی وجود نداشته باشد، درخواست‌ها هدر می‌روند و ممکن است اطلاعات با کمی تأخیر به کاربر برسند.

۲. Long Polling (نظرسنجی طولانی)

در این روش، کلاینت درخواست می‌فرستد، اما سرور تا زمان آماده‌شدن اطلاعات جدید یا رسیدن به یک مهلت مشخص، پاسخ را نگه می‌دارد. پس از دریافت پاسخ، کلاینت بلافاصله درخواست دیگری ارسال می‌کند. این روش تعداد درخواست‌های غیرضروری را نسبت به Polling معمولی کاهش می‌دهد و برای اعلان‌ها و چت کاربرد دارد؛ بااین‌حال، همچنان درخواست‌ها و پاسخ‌های HTTP به‌صورت جداگانه برقرار می‌شوند.

۳. WebSocket

WebSocket یک ارتباط دوطرفه و پایدار بین کلاینت و سرور ایجاد می‌کند. ارتباط معمولاً با یک درخواست HTTP آغاز می‌شود و سپس به WebSocket ارتقا پیدا می‌کند. بعد از برقراری ارتباط، هر دو طرف می‌توانند بدون نیاز به ارسال یک درخواست HTTP جدید برای هر پیام، اطلاعات را برای طرف مقابل بفرستند. این روش برای چت آنلاین، بازی‌های آنلاین و برنامه‌هایی که به تبادل سریع اطلاعات نیاز دارند، مناسب است.

۴. Server-Sent Events (SSE)

در این روش، کلاینت یک اتصال HTTP برقرار می‌کند و سرور می‌تواند از طریق همان اتصال، رویدادها و اطلاعات جدید را به‌صورت پیوسته برای کلاینت ارسال کند. ارتباط در SSE یک‌طرفه است؛ یعنی سرور اطلاعات را به کلاینت می‌فرستد و برای ارسال اطلاعات از کلاینت به سرور باید از درخواست‌های جداگانه استفاده شود. این روش برای اعلان‌ها، نمایش وضعیت پردازش و به‌روزرسانی زندهٔ اطلاعات مناسب است.

۵. Webhook

در Webhook، یک برنامه یا سرویس، یک نشانی مشخص از سرویس مقصد دریافت می‌کند و هنگام رخ‌دادن یک رویداد، یک درخواست HTTP، معمولاً از نوع POST، به آن نشانی می‌فرستد. برای مثال، بعد از موفقیت‌آمیزشدن پرداخت، درگاه پرداخت می‌تواند نتیجه را به آدرس ثبت‌شدهٔ فروشگاه ارسال کند. در این روش، لازم نیست سرویس مقصد دائماً وضعیت را بررسی کند؛ اما باید یک نشانی قابل‌دسترسی داشته باشد و بتواند درخواست‌های دریافتی را پردازش کند. Webhook بیشتر برای ارتباط بین سرویس‌ها کاربرد دارد، نه ارسال مستقیم اطلاعات به مرورگر کاربر.

این روش‌ها بسته به نوع کاربرد انتخاب می‌شوند: برای ارتباط دوطرفه و لحظه‌ای معمولاً WebSocket، برای ارسال یک‌طرفهٔ رویدادها SSE، و برای اطلاع‌رسانی بین سرویس‌ها Webhook گزینه‌های مناسبی هستند.

سؤال ۴: مشخص‌کردن اجزای یوآرال

آدرس موردنظر:ss://asghar:1234!!@ss.myproxy.com:1234#shadowSocks1


اجزای آدرس:

۱. نوع پروتکل (Scheme): ss

۲. نام کاربری (Username): asghar

۳. رمز عبور (Password): 1234!!

۴. نام میزبان (Host): ss.myproxy.com

۵. شماره پورت (Port): 1234

۶. بخش Fragment: shadowSocks1

نکته: علامت @ اطلاعات کاربری را از نام میزبان جدا می‌کند. علامت : برای جداکردن نام کاربری از رمز عبور و نام میزبان از شماره پورت استفاده شده است. علامت # نیز شروع بخش Fragment را مشخص می‌کند. در این آدرس، Fragment ممکن است توسط برنامه مربوط به این پروتکل به‌عنوان نام نمایشی یا برچسب استفاده شود


سؤال ۵: انتخاب Status Code مناسب برای REST API

۱. دیتابیس سایت مشکل پیدا کرده و درخواست‌های ورود انجام نمی‌شوند.

کد پیشنهادی: 503 Service Unavailable

چون مشکل از سمت سرور است و سرویس فعلاً قادر به پاسخ‌گویی صحیح نیست. کد 503 برای مشکلات موقت، مثل از دسترس خارج‌شدن یک سرویس وابسته یا اضافه‌بار سرور، مناسب است.

۲. نام کاربری واردشده در سایت وجود ندارد و ورود موفق نیست.

کد پیشنهادی: 401 Unauthorized

چون اطلاعات احراز هویت معتبر نیست و ورود انجام نشده است. بهتر است پیام خطا به‌گونه‌ای باشد که وجود یا نبود یک نام کاربری مشخص را به افراد دیگر افشا نکند؛ بنابراین می‌توان برای نام کاربری ناموجود و رمز عبور اشتباه، پیام یکسانی برگرداند.

۳. وب‌سایت به دامنهٔ دیگری منتقل شده است.

کد پیشنهادی: 301 Moved Permanently

چون انتقال دائمی است و آدرس جدید باید در هدر Location قرار بگیرد تا کلاینت بتواند به آن هدایت شود. اگر حفظ متد درخواست، مثلاً POST، اهمیت داشته باشد، کد 308 Permanent Redirect هم انتخاب مناسبی است؛ زیرا متد درخواست را تغییر نمی‌دهد.

۴. تعداد درخواست‌های کاربر از نرخ مجاز بیشتر شده است.

کد پیشنهادی: 429 Too Many Requests

این کد دقیقاً برای زمانی است که کلاینت در یک بازهٔ زمانی تعداد درخواست بیش از حد مجاز ارسال می‌کند. در صورت نیاز، سرور می‌تواند هدر Retry-After را هم ارسال کند تا زمان تقریبی تلاش مجدد مشخص شود.

۵. تمدید JWT موفق بوده و توکن جدید در هدر پاسخ قرار گرفته است.

کد پیشنهادی: 200 OK
چون عملیات با موفقیت انجام شده و پاسخ موفقی به کلاینت برگردانده می‌شود. توکن جدید می‌تواند در یکی از هدرهای پاسخ قرار بگیرد. اگر پاسخ هیچ محتوایی نداشته باشد و فقط هدرها اهمیت داشته باشند، کد 204 No Content نیز می‌تواند مناسب باشد؛ اما برای این سناریو 200 انتخاب عمومی‌تری است.

۶. کاربر از یک محدودهٔ IP ممنوعه برای دسترسی به سرویس استفاده می‌کند.

کد پیشنهادی: 403 Forbidden
چون سرور درخواست را دریافت کرده، اما اجازهٔ دسترسی به سرویس را به این کاربر یا IP نمی‌دهد. اگر علت عدم دسترسی به‌طور مشخص یک محدودیت قانونی باشد، کد 451 Unavailable For Legal Reasons نیز می‌تواند مناسب باشد. برای محدودیت IP که صرفاً بر اساس سیاست دسترسی سرویس اعمال شده است، 403 انتخاب معمول‌تری است.


سؤال ۶: مشخص‌کردن نوع پروکسی
۱. استفاده از سرورهای داخلی دانشگاه برای دریافت پکیج‌ها به‌جای سرورهای مرکزی
نوع: Caching Proxy / Repository Mirror
در این روش، نسخه‌ای از پکیج‌ها روی سرور داخلی دانشگاه نگهداری می‌شود. کاربران به‌جای دریافت مستقیم پکیج‌ها از سرور اصلی، آن‌ها را از سرور داخلی دریافت می‌کنند. این کار باعث کاهش مصرف پهنای باند اینترنت، افزایش سرعت دانلود و کاهش بار روی سرور اصلی می‌شود. اگر مخزن داخلی نسخه‌ای از مخزن اصلی باشد، اصطلاح Repository Mirror هم برای آن استفاده می‌شود.

۲. تقسیم درخواست‌ها بر اساس مبدأ جغرافیایی درخواست‌ها
نوع: Reverse Proxy با مسیریابی جغرافیایی (Geo-based Routing)
در این روش، درخواست‌های کاربران با توجه به موقعیت جغرافیایی آن‌ها به سرور مناسب هدایت می‌شوند. برای مثال، درخواست کاربران اروپا به سروری در اروپا فرستاده می‌شود تا تأخیر ارتباط کاهش پیدا کند. این قابلیت ممکن است با استفاده از Reverse Proxy، سامانهٔ توزیع بار یا سرویس‌های GeoDNS پیاده‌سازی شود

۳. اضافه‌کردن قابلیت احراز هویت به یک سرویس بسیار قدیمی
نوع: Authentication Proxy (معمولاً Reverse Proxy)
در این روش، یک پروکسی جلوی سرویس قدیمی قرار می‌گیرد و قبل از عبور دادن درخواست به سرویس اصلی، هویت کاربر را بررسی می‌کند. به این ترتیب، می‌توان بدون تغییر اساسی در کد سرویس قدیمی، قابلیت احراز هویت را به آن اضافه کرد. اگر احراز هویت موفق باشد، پروکسی درخواست را به سرویس اصلی می‌فرستد و در غیر این صورت، دسترسی را رد می‌کند.
