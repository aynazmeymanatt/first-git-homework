# تمرین Git

## سوال ۱: تفاوت git merge و git rebase

### git merge چیست؟
دستور git merge تغییرات یک شاخه (branch) را با شاخهٔ دیگر ترکیب می‌کند. 
در این روش، Git یک کامیت ادغام (merge commit) جدید می‌سازد که دو والد دارد: 
یکی از شاخهٔ فعلی و دیگری از شاخه‌ای که ادغام می‌شود.

شکل تاریخچه: تاریخچهٔ کامیت‌ها به‌صورت غیرخطی (non-linear) باقی می‌ماند و 
شاخه‌ها در تاریخچه قابل مشاهده هستند.

### git rebase چیست؟
دستور git rebase کامیت‌های یک شاخه را برمی‌دارد و آن‌ها را روی نوک شاخهٔ دیگر 
دوباره اعمال می‌کند. در واقع تاریخچه را بازنویسی می‌کند و کامیت‌های جدیدی با 
همان محتوا ولی هش (hash) متفاوت می‌سازد.

شکل تاریخچه: تاریخچه خطی (linear) و تمیز می‌شود؛ انگار همهٔ کارها 
پشت سر هم روی یک شاخه انجام شده است.

### تفاوت‌های اصلی
در git merge تاریخچه به‌صورت غیرخطی باقی می‌ماند و یک merge commit اضافه می‌شود، 
اما در git rebase تاریخچه خطی و تمیز می‌شود و کامیت جدیدی اضافه نمی‌شود بلکه 
کامیت‌های قبلی بازنویسی می‌شوند.

در git merge هش کامیت‌ها تغییر نمی‌کند و تاریخچه دست‌نخورده می‌ماند، 
اما در git rebase هش کامیت‌ها تغییر می‌کند چون تاریخچه بازنویسی می‌شود.

### چه موقع از merge استفاده کنیم؟
- وقتی می‌خواهیم تاریخچهٔ واقعی و کامل پروژه حفظ شود.
- وقتی شاخه‌ای که ادغام می‌شود عمومی است و دیگران هم روی آن کار می‌کنند.
- وقتی نمی‌خواهیم هش کامیت‌های قبلی تغییر کند.
- در پروژه‌های تیمی که چند نفر روی یک شاخه کار می‌کنند.

چرا؟ چون merge تاریخچه را دست‌نخورده نگه می‌دارد و باعث دردسر برای 
هم‌تیمی‌ها نمی‌شود.

### چه موقع از rebase استفاده کنیم؟
- وقتی می‌خواهیم تاریخچه تمیز و خطی باشد.
- وقتی روی یک شاخهٔ شخصی کار می‌کنیم و هنوز آن را push نکرده‌ایم.
- قبل از ادغام نهایی، برای مرتب‌کردن کامیت‌های خودمان.
- برای به‌روزرسانی شاخهٔ کاری با آخرین تغییرات شاخهٔ اصلی.

چرا؟ چون rebase تاریخچه را خطی و خوانا می‌کند و از شر merge commitهای 
اضافی خلاص می‌شود. البته چون تاریخچه را بازنویسی می‌کند، نباید روی شاخه‌های 
عمومی استفاده شود.

### نتیجه‌گیری
merge برای حفظ تاریخچهٔ واقعی و امن برای شاخه‌های عمومی مناسب است.
rebase برای داشتن تاریخچهٔ خطی و تمیز و مناسب برای شاخه‌های شخصی است.
قانون طلایی: روی شاخه‌های عمومی rebase نکن.


## سوال ۲: انتخاب بخشی از تغییرات

### hunk (بخش تغییرات) چیست؟
وقتی در Git تغییری در یک فایل ایجاد می‌شود و دستور `git diff` را اجرا می‌کنیم، 
Git تغییرات را به صورت چند بخش مجزا نمایش می‌دهد. به هر یک از این بخش‌ها 
یک hunk (بخش تغییرات) گفته می‌شود. هر hunk معمولاً شامل چند خط پشت سر هم است 
که در یک ناحیه از فایل تغییر کرده‌اند. Git این بخش‌ها را بر اساس نزدیکی خطوط 
تغییر یافته به یکدیگر جدا می‌کند تا بتوانیم هر بخش را جداگانه بررسی یا stage کنیم.

### بررسی تعاملی تغییرات با خط فرمان
برای اینکه تغییرات یک فایل را به صورت تعاملی بررسی کنیم و فقط بعضی از 
بخش‌ها را برای کامیت بعدی در ناحیه staging قرار دهیم، از دستور زیر استفاده می‌کنیم:

git add -p

یا معادل کامل آن:

git add --patch

با اجرای این دستور، Git هر hunk را یکی‌یکی به ما نشان می‌دهد و می‌پرسد 
که می‌خواهیم آن را stage کنیم یا نه. در هر مرحله می‌توانیم یکی از گزینه‌های 
زیر را انتخاب کنیم:

y به معنی بله، این hunk را stage کن.
n به معنی نه، این hunk را stage نکن.
q به معنی خروج از حالت تعاملی بدون stage کردن بقیه.
a به معنی stage کردن این hunk و همهٔ hunkهای بعدی این فایل.
d به معنی stage نکردن این hunk و همهٔ hunkهای بعدی این فایل.
s به معنی تقسیم این hunk به بخش‌های کوچک‌تر.
e به معنی ویرایش دستی این hunk.

### مراحل انجام کار
۱. فایل مورد نظر را تغییر بده.
۲. دستور git add -p را اجرا کن.
۳. برای هر hunk یکی از گزینه‌های بالا را انتخاب کن.
۴. بعد از اتمام، دستور git diff --staged را بزن تا ببینی چه بخش‌هایی stage شده‌اند.
۵. با git commit تغییرات stage شده را کامیت کن.

### فایدهٔ این کار برای ساختن کامیت‌های منسجم
با استفاده از git add -p می‌توانیم تغییراتی را که به هم مربوط نیستند از هم جدا کنیم 
و هر گروه را در یک کامیت مستقل ثبت کنیم. این کار باعث می‌شود:

- هر کامیت فقط یک تغییر منطقی و مشخص را شامل شود.
- تاریخچهٔ پروژه خواناتر و قابل فهم‌تر باشد.
- در صورت نیاز به برگرداندن یک تغییر، فقط همان کامیت مربوطه revert شود 
  و بقیهٔ تغییرات دست‌نخورده بمانند.
- بررسی کد در code review راحت‌تر شود.
- پیام کامیت‌ها معنادارتر و دقیق‌تر باشند.

به همین دلیل، انتخاب بخشی از تغییرات (hunk) یکی از مهارت‌های مهم در استفادهٔ 
حرفه‌ای از Git است و به منسجم ماندن تاریخچهٔ پروژه کمک زیادی می‌کند.
