# تمرین Git

## سوال ۱: تفاوت git merge و git rebase

### git merge چیست؟
دستور git merge تغییرات یک شاخه (branch) را با شاخهٔ دیگر ترکیب می‌کند. 
در این روش، Git یک کامیت ادغام (merge commit) جدید می‌سازد که دو والد دارد: 
یکی از شاخهٔ فعلی و دیگری از شاخه‌ای که ادغام می‌شود.

شکل تاریخچه: تاریخچهٔ کامیت‌ها به‌صورت غیرخطی (non-linear) باقی می‌ماند و 
شاخه‌ها در تاریخچه قابل مشاهده هستند.

### git rebase چیست؟
دستور git rebase کامیت‌های یک شاخه را برمی‌دارد و آن‌ها را روی نوک شاخهٔ دیگر 
دوباره اعمال می‌کند. در واقع تاریخچه را بازنویسی می‌کند و کامیت‌های جدیدی با 
همان محتوا ولی هش (hash) متفاوت می‌سازد.

شکل تاریخچه: تاریخچه خطی (linear) و تمیز می‌شود؛ انگار همهٔ کارها 
پشت سر هم روی یک شاخه انجام شده است.

### تفاوت‌های اصلی
در git merge تاریخچه به‌صورت غیرخطی باقی می‌ماند و یک merge commit اضافه می‌شود، 
اما در git rebase تاریخچه خطی و تمیز می‌شود و کامیت جدیدی اضافه نمی‌شود بلکه 
کامیت‌های قبلی بازنویسی می‌شوند.

در git merge هش کامیت‌ها تغییر نمی‌کند و تاریخچه دست‌نخورده می‌ماند، 
اما در git rebase هش کامیت‌ها تغییر می‌کند چون تاریخچه بازنویسی می‌شود.

### چه موقع از merge استفاده کنیم؟
- وقتی می‌خواهیم تاریخچهٔ واقعی و کامل پروژه حفظ شود.
- وقتی شاخه‌ای که ادغام می‌شود عمومی است و دیگران هم روی آن کار می‌کنند.
- وقتی نمی‌خواهیم هش کامیت‌های قبلی تغییر کند.
- در پروژه‌های تیمی که چند نفر روی یک شاخه کار می‌کنند.

چرا؟ چون merge تاریخچه را دست‌نخورده نگه می‌دارد و باعث دردسر برای 
هم‌تیمی‌ها نمی‌شود.

### چه موقع از rebase استفاده کنیم؟
- وقتی می‌خواهیم تاریخچه تمیز و خطی باشد.
- وقتی روی یک شاخهٔ شخصی کار می‌کنیم و هنوز آن را push نکرده‌ایم.
- قبل از ادغام نهایی، برای مرتب‌کردن کامیت‌های خودمان.
- برای به‌روزرسانی شاخهٔ کاری با آخرین تغییرات شاخهٔ اصلی.

چرا؟ چون rebase تاریخچه را خطی و خوانا می‌کند و از شر merge commitهای 
اضافی خلاص می‌شود. البته چون تاریخچه را بازنویسی می‌کند، نباید روی شاخه‌های 
عمومی استفاده شود.

### نتیجه‌گیری
merge برای حفظ تاریخچهٔ واقعی و امن برای شاخه‌های عمومی مناسب است.
rebase برای داشتن تاریخچهٔ خطی و تمیز و مناسب برای شاخه‌های شخصی است.
قانون طلایی: روی شاخه‌های عمومی rebase نکن.


## سوال ۲: انتخاب بخشی از تغییرات

### hunk (بخش تغییرات) چیست؟
وقتی در Git تغییری در یک فایل ایجاد می‌شود و دستور `git diff` را اجرا می‌کنیم، 
Git تغییرات را به صورت چند بخش مجزا نمایش می‌دهد. به هر یک از این بخش‌ها 
یک hunk (بخش تغییرات) گفته می‌شود. هر hunk معمولاً شامل چند خط پشت سر هم است 
که در یک ناحیه از فایل تغییر کرده‌اند. Git این بخش‌ها را بر اساس نزدیکی خطوط 
تغییر یافته به یکدیگر جدا می‌کند تا بتوانیم هر بخش را جداگانه بررسی یا stage کنیم.

### بررسی تعاملی تغییرات با خط فرمان
برای اینکه تغییرات یک فایل را به صورت تعاملی بررسی کنیم و فقط بعضی از 
بخش‌ها را برای کامیت بعدی در ناحیه staging قرار دهیم، از دستور زیر استفاده می‌کنیم:

git add -p

یا معادل کامل آن:

git add --patch

با اجرای این دستور، Git هر hunk را یکی‌یکی به ما نشان می‌دهد و می‌پرسد 
که می‌خواهیم آن را stage کنیم یا نه. در هر مرحله می‌توانیم یکی از گزینه‌های 
زیر را انتخاب کنیم:

y به معنی بله، این hunk را stage کن.
n به معنی نه، این hunk را stage نکن.
q به معنی خروج از حالت تعاملی بدون stage کردن بقیه.
a به معنی stage کردن این hunk و همهٔ hunkهای بعدی این فایل.
d به معنی stage نکردن این hunk و همهٔ hunkهای بعدی این فایل.
s به معنی تقسیم این hunk به بخش‌های کوچک‌تر.
e به معنی ویرایش دستی این hunk.

### مراحل انجام کار
۱. فایل مورد نظر را تغییر بده.
۲. دستور git add -p را اجرا کن.
۳. برای هر hunk یکی از گزینه‌های بالا را انتخاب کن.
۴. بعد از اتمام، دستور git diff --staged را بزن تا ببینی چه بخش‌هایی stage شده‌اند.
۵. با git commit تغییرات stage شده را کامیت کن.

### فایدهٔ این کار برای ساختن کامیت‌های منسجم
با استفاده از git add -p می‌توانیم تغییراتی را که به هم مربوط نیستند از هم جدا کنیم 
و هر گروه را در یک کامیت مستقل ثبت کنیم. این کار باعث می‌شود:

- هر کامیت فقط یک تغییر منطقی و مشخص را شامل شود.
- تاریخچهٔ پروژه خواناتر و قابل فهم‌تر باشد.
- در صورت نیاز به برگرداندن یک تغییر، فقط همان کامیت مربوطه revert شود 
  و بقیهٔ تغییرات دست‌نخورده بمانند.
- بررسی کد در code review راحت‌تر شود.
- پیام کامیت‌ها معنادارتر و دقیق‌تر باشند.

به همین دلیل، انتخاب بخشی از تغییرات (hunk) یکی از مهارت‌های مهم در استفادهٔ 
حرفه‌ای از Git است و به منسجم ماندن تاریخچهٔ پروژه کمک زیادی می‌کند.


## سوال ۳: یافتن منشأ خطا با git bisect

### git bisect چیست و چگونه کار می‌کند؟
دستور git bisect یک ابزار برای پیدا کردن کامیتی است که یک خطا (bug) را وارد 
پروژه کرده است. این دستور از روش جست‌وجوی دودویی (binary search) استفاده می‌کند؛ 
یعنی به جای بررسی تک‌تک کامیت‌ها، محدودهٔ کامیت‌ها را نصف می‌کند و هر بار 
وسط محدوده را بررسی می‌کند تا در نهایت به کامیت معیوب برسد.

این روش بسیار سریع‌تر از بررسی خطی کامیت‌هاست. مثلاً اگر بین ۱۰۰۰ کامیت 
دنبال کامیت معیوب باشیم، با جست‌وجوی خطی ممکن است تا ۱۰۰۰ بار بررسی لازم باشد، 
اما با git bisect فقط حدود ۱۰ بار (log₂ ۱۰۰۰) کافی است.

### مراحل پیدا کردن کامیت معیوب

۱. ابتدا باید یک کامیت سالم (good) و یک کامیت معیوب (bad) را مشخص کنیم. 
   کامیت bad معمولاً همان کامیت فعلی (HEAD) است که در آن خطا وجود دارد، 
   و کامیت good یک کامیت قدیمی‌تر است که در آن خطا وجود نداشته.

۲. دستور git bisect start را اجرا می‌کنیم تا فرایند جست‌وجو شروع شود.

۳. با دستور git bisect bad کامیت معیوب را مشخص می‌کنیم.

۴. با دستور git bisect good <commit> کامیت سالم را مشخص می‌کنیم. 
   به جای <commit> می‌توانیم هش کامیت، نام تگ یا نام شاخه را بدهیم.

۵. Git به صورت خودکار یک کامیت میانی را checkout می‌کند و از ما می‌پرسد 
   که آیا در این کامیت خطا وجود دارد یا نه. ما باید پروژه را تست کنیم و 
   سپس یکی از دو دستور زیر را بزنیم:

   git bisect good   (اگر در این کامیت خطا نبود)
   git bisect bad    (اگر در این کامیت خطا وجود داشت)

۶. Git این روند را ادامه می‌دهد و هر بار محدودهٔ جست‌وجو را نصف می‌کند 
   تا در نهایت به کامیتی برسد که اولین بار خطا را وارد کرده است. 
   در این مرحله Git پیامی مشابه زیر نمایش می‌دهد:

   <commit-hash> is the first bad commit

۷. در پایان با دستور git bisect reset از حالت bisect خارج می‌شویم و 
   به شاخهٔ اصلی برمی‌گردیم.

### مثال از کاربرد git bisect
فرض کنید در یک پروژهٔ نرم‌افزاری، تابعی به نام calculatePrice به تازگی 
خراب شده و خروجی اشتباه می‌دهد. نمی‌دانیم کدام کامیت این خطا را وارد کرده است. 
کامیت فعلی (HEAD) معیوب است و آخرین کامیت قبل از انتشار نسخهٔ پایدار 
(مثلاً تگ v1.0) سالم بوده است. مراحل به این صورت است:

git bisect start
git bisect bad
git bisect good v1.0

سپس Git یک کامیت میانی را checkout می‌کند. ما پروژه را تست می‌کنیم و 
اگر خروجی درست بود git bisect good و اگر خراب بود git bisect bad می‌زنیم. 
این کار را ادامه می‌دهیم تا Git کامیت معیوب را پیدا کند. در نهایت:

git bisect reset

### چرا این روش برای یافتن منشأ خطا مفید است؟
- سرعت بسیار بالا به دلیل استفاده از جست‌وجوی دودویی به جای جست‌وجوی خطی.
- کاهش چشمگیر تعداد کامیت‌هایی که باید دستی تست شوند.
- مناسب برای پروژه‌های بزرگ با تاریخچهٔ طولانی.
- امکان خودکارسازی با دستور git bisect run برای اجرای یک اسکریپت تست.
- کمک به پیدا کردن دقیق کامیت معیوب بدون نیاز به بررسی دستی همهٔ کامیت‌ها.

## سوال ۴: بررسی تغییرات پیش از کامیت

### قسمت ۱: بررسی وضعیت مخزن
برای دیدن تغییرات هنوز وارد نشده به ناحیه staging و تغییرات آمادهٔ کامیت، 
دو دستور اصلی داریم:

git status
git diff
git diff --staged

دستور git status به‌طور کلی نشان می‌دهد چه فایل‌هایی تغییر کرده‌اند، کدام‌ها 
stage شده‌اند و کدام‌ها هنوز stage نشده‌اند. اما این دستور فقط اسم فایل‌ها 
و وضعیت کلی آن‌ها را نشان می‌دهد، نه محتوای دقیق تغییرات را.

دستور git diff تغییرات هنوز stage نشده را نشان می‌دهد. یعنی چیزهایی که 
در فایل تغییر داده‌ایم ولی هنوز با git add آن‌ها را به staging نفرستاده‌ایم.

دستور git diff --staged تغییرات آمادهٔ کامیت را نشان می‌دهد. یعنی چیزهایی که 
با git add به staging اضافه شده‌اند و اگر همین حالا کامیت بزنیم، در کامیت 
قرار می‌گیرند.

تفاوت این دو دسته: git diff تغییرات «هنوز آماده‌نشده» را نشان می‌دهد، ولی 
git diff --staged تغییرات «آمادهٔ کامیت» را. در سناریوی سوال، چون بخشی از 
تغییرات را stage کرده‌ایم و بعد دوباره فایل را ویرایش کرده‌ایم، git diff 
تغییرات جدیدی که بعد از stage کردن اضافه شده را نشان می‌دهد و 
git diff --staged همان تغییرات قبلی stage شده را.

### قسمت ۲: اگر الان کامیت معمولی بزنیم چه می‌شود؟
اگر بدون گزینه -a یک کامیت معمولی بزنیم، فقط تغییراتی که قبلاً در ناحیهٔ 
staging قرار داده‌ایم در کامیت ثبت می‌شوند. تغییراتی که بعد از stage کردن 
روی فایل انجام داده‌ایم، در کامیت قرار نمی‌گیرند و در working directory 
باقی می‌مانند.

دلیلش این است که Git کامیت را از روی ناحیهٔ staging می‌سازد، نه از روی 
فایل‌های فعلی working directory. کامیت معمولی فقط چیزهایی را ثبت می‌کند 
که با git add به staging اضافه شده‌اند.

اگر از git commit -a استفاده کنیم، Git به‌طور خودکار همهٔ فایل‌های tracked 
که تغییر کرده‌اند را هم stage می‌کند و همه با هم در کامیت می‌آیند. اما 
فایل‌های untracked و جدید همچنان نادیده گرفته می‌شوند.

### قسمت ۳: جلوگیری از اضافه شدن فایل‌های /tmp
برای اینکه فایل‌های داخل پوشهٔ /tmp به کامیت‌های بعدی اضافه نشوند، باید 
یک فایل به نام .gitignore در ریشهٔ مخزن بسازیم و مسیر آن پوشه را داخلش بنویسیم:

tmp/

یا اگر فقط یک پوشه در ریشهٔ مخزن مدنظر است:

/tmp/

این فایل به Git می‌گوید این مسیرها را نادیده بگیر و در git status و 
کامیت‌ها نمایش نده.

نکتهٔ مهم: این تنظیم فقط برای فایل‌هایی کار می‌کند که قبلاً tracked نشده باشند. 
اگر فایلی قبلاً tracked شده باشد و در .gitignore هم باشد، Git همچنان آن را 
دنبال می‌کند و در تغییرات نشان می‌دهد. برای اینکه یک فایل tracked را 
از حالت tracked خارج کنیم، باید با دستور زیر آن را از ایندکس حذف کنیم:

git rm --cached <file>

بعد از این دستور، فایل از مخزن Git حذف می‌شود ولی روی دیسک باقی می‌ماند. 
از آن به بعد .gitignore روی آن اثر می‌گذارد و دیگر در کامیت‌ها نمی‌آید.

## سوال ۵: رفع merge conflict در کار گروهی

### قسمت ۱: چرا conflict رخ داده؟
conflict وقتی پیش می‌آید که دو نفر (یا دو شاخه) یک خط مشترک از یک فایل را 
به دو شکل متفاوت تغییر داده باشند. در این حالت Git نمی‌داند کدام نسخه را 
انتخاب کند، چون هر دو تغییر از یک کامیت مشترک شروع شده‌اند و هر کدام یک 
مسیر متفاوت را رفته‌اند.

اما نه، هر تغییری که دو نفر در یک فایل ایجاد کنند باعث conflict نمی‌شود. 
اگر دو نفر خطوط مختلفی از فایل را تغییر داده باشند، Git می‌تواند هر دو تغییر 
را خودش ترکیب کند و conflict نمی‌دهد. conflict فقط وقتی رخ می‌دهد که هر دو 
نفر دقیقاً یک خط یا یک ناحیهٔ نزدیک به هم را متفاوت تغییر داده باشند.

### قسمت ۲: شناسایی فایل‌های دارای conflict و نقش conflict markers
بعد از اجرای merge، دستور git status فایل‌های دارای conflict را نشان می‌دهد. 
این فایل‌ها زیر عنوان "Unmerged paths" لیست می‌شوند.

اگر فایل را باز کنیم، Git داخل آن نشانه‌هایی به نام conflict markers می‌گذارد 
که به این شکل هستند:

<<<<<<< HEAD
متن نسخهٔ شاخهٔ فعلی (مثلاً main)
=======
متن نسخهٔ شاخهٔ در حال ادغام (مثلاً feature-description)
>>>>>>> feature-description

این نشانه‌ها به ما می‌گویند کدام خطوط مربوط به کدام نسخه است. بخش بین 
<<<<<<< HEAD و ======= نسخهٔ شاخهٔ ماست و بخش بین ======= و >>>>>>> 
نسخهٔ شاخهٔ دیگر است.

### قسمت ۳: مراحل کامل کردن merge با حفظ هر دو تغییر
اگر بخواهیم اطلاعات هر دو تغییر حفظ شود، این مراحل را انجام می‌دهیم:

۱. فایل دارای conflict را در VS Code یا هر ویرایشگر دیگری باز می‌کنیم.

۲. خطوط conflict markers را پاک می‌کنیم و به‌جای آن‌ها هر دو متن را 
   به شکلی که می‌خواهیم نگه می‌داریم. یعنی هر دو نسخه را کنار هم می‌نویسیم 
   یا ترکیب می‌کنیم.

۳. فایل را ذخیره می‌کنیم.

۴. فایل را با دستور git add به staging اضافه می‌کنیم:

git add README.md

۵. اگر فایل دیگری هم conflict داشت، همین کار را برایش تکرار می‌کنیم.

۶. دستور git commit را می‌زنیم تا merge کامل شود. Git یک merge commit 
   می‌سازد و پیام پیش‌فرضی برای آن می‌گذارد.

برای اطمینان از اینکه conflict markers در متن نهایی باقی نمانده‌اند، 
می‌توانیم دستور زیر را بزنیم:

git diff --check

این دستور خطوطی که هنوز نشانه‌های conflict دارند را نشان می‌دهد. اگر 
خروجی خالی بود، یعنی هیچ conflict marker باقی نمانده است. همچنین می‌توانیم 
دستی فایل را دوباره باز کنیم و مطمئن شویم نشانه‌هایی مثل <<<<<<< یا ======= 
یا >>>>>>> در متن نیستند.

### قسمت ۴: لغو merge در حال انجام
اگر وسط merge متوجه شدیم که نباید این merge انجام شود، با دستور زیر 
عملیات merge را لغو می‌کنیم:

git merge --abort

این دستور همه چیز را به حالت قبل از شروع merge برمی‌گرداند. یعنی فایل‌ها 
به وضعیت قبلی برمی‌گردند، تغییرات merge لغو می‌شود و مخزن به حالت clean 
قبل از merge برمی‌گردد.


## سوال ۶: انتخاب روش مناسب برای بازگرداندن تغییرات

### موقعیت ۱: تغییر در فایل tracked که در staging نیست و آن را نمی‌خواهیم
در این حالت فقط در working directory تغییر ایجاد کرده‌ایم و هنوز آن را 
stage نکرده‌ایم. نسخهٔ staging همان آخرین کامیت است. می‌خواهیم فقط تغییرات 
همین فایل کنار گذاشته شود و بقیهٔ فایل‌ها دست نخورده بمانند.

دستور مناسب:

git restore notes.txt

یا در نسخه‌های قدیمی‌تر Git:

git checkout -- notes.txt

اثر این دستور: فایل notes.txt در working directory به همان نسخهٔ آخرین 
کامیت (یا نسخهٔ staging) برمی‌گردد و تغییرات این فایل از بین می‌رود. 
ناحیهٔ staging و تاریخچهٔ کامیت‌ها دست‌نخورده می‌مانند. فایل‌های دیگر 
هم تغییری نمی‌کنند.

### موقعیت ۲: تغییرات را اشتباهاً stage کرده‌ایم ولی کامیت نکرده‌ایم
در این حالت تغییرات در staging هستند ولی هنوز کامیت نشده‌اند. می‌خواهیم 
فایل از staging خارج شود ولی ویرایش‌های ما در working directory حفظ شوند.

دستور مناسب:

git restore --staged notes.txt

یا در نسخه‌های قدیمی‌تر Git:

git reset HEAD notes.txt

اثر این دستور: فایل notes.txt از ناحیهٔ staging خارج می‌شود ولی تغییراتش 
در working directory باقی می‌ماند. یعنی انگار دوباره فقط تغییر lokal داریم 
و هنوز stage نشده. تاریخچهٔ کامیت‌ها تغییری نمی‌کند.

### موقعیت ۳: کامیت اشتباه را push کرده‌ایم و هم‌تیمی‌ها هم آن را دریافت کرده‌اند
در این حالت یک کامیت اشتباه (نه merge commit) روی شاخهٔ main push شده و 
همه آن را دارند. working tree هم clean است. می‌خواهیم اثر این کامیت را 
بدون حذف یا بازنویسی تاریخچه برگردانیم.

روش مناسب: استفاده از دستور git revert

مراحل:
۱. ابتدا هش کامیت اشتباه را پیدا می‌کنیم:

git log --oneline

۲. سپس دستور زیر را می‌زنیم:

git revert <commit-hash>

Git یک کامیت جدید می‌سازد که دقیقاً برعکس کامیت اشتباه است. یعنی 
تغییراتی که آن کامیت اضافه کرده بود را برمی‌گرداند.

۳. سپس تغییرات را push می‌کنیم:

git push

اثر این دستور: یک کامیت جدید به تاریخچه اضافه می‌شود که اثر کامیت اشتباه 
را خنثی می‌کند، ولی خود کامیت اشتباه در تاریخچه باقی می‌ماند. تاریخچه 
بازنویسی نمی‌شود و بقیهٔ هم‌تیمی‌ها بدون مشکل می‌توانند ادامه دهند.

چرا حذف کامیت از تاریخچه و force push مناسب نیست؟
چون کامیت اشتباه را push کرده‌ایم و هم‌تیمی‌ها هم آن را دریافت کرده‌اند. 
اگر تاریخچه را بازنویسی کنیم و با force push آن را به GitHub بفرستیم، 
تاریخچهٔ محلی ما با تاریخچهٔ هم‌تیمی‌ها فرق می‌کند و باعث می‌شود 
برای آن‌ها conflict و مشکل‌های جدی پیش بیاید. در واقع تاریخچهٔ مشترک 
دست‌کاری شده و هم‌تیمی‌ها نمی‌توانند به‌راحتی تغییراتشان را push کنند.

به همین دلیل، در شاخه‌های عمومی و مشترک مثل main، همیشه باید از 
git revert استفاده کنیم، نه از حذف کامیت و force push. force push فقط 
برای شاخه‌های شخصی که هنوز push نشده‌اند یا فقط خودمان روی آن کار می‌کنیم 
مناسب است.
